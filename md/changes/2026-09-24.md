## Instore Products served from a stored read model

**Time:** 14:20 SAST

**Summary.** Instore Products was rebuilt from source on every customer
request: a complete paged read of `extended_range_items` (5,336 rows today), a
complete paged read of `website_stock` (6,069 rows) for the duplicate gate, then
the image, price, stock, duplicate and classification rules in JavaScript —
roughly 4,200 products classified and ~150 million identifier comparisons before
the first of sixty products could be shown. The already-gated result is now kept
in its own table in the stock database and a browse or search request reads one
small page from it.

Customer-visible behaviour is unchanged: the same eligibility rules, the same
product objects, the same browse tiles, the same search matching and ranking,
the same paging, the same `source` label and the same response shape. Nothing
about checkout or the live "Check stock" button changed.

**How it works.**

- `api/instore-catalogue-refresh.js` (new) runs the same live read the customer
  API runs and stores its result: one row per eligible product holding that
  product's exact response payload, its browse category, its search tokens and
  its position in the default customer ordering, plus the browse tiles for the
  whole collection. Rows are staged and swapped in one transaction, so a
  half-written or empty collection can never be served.
- `api/extended-range.js` serves from that table when the snapshot is fresh and
  was built under the Instore image/listing controls currently in force. A
  landing or category page is ordered, paged and counted by the database. A
  search is still matched and ranked by the application; the database only
  narrows the collection to the stored token matches first, in SKU order, which
  is the order equal-scoring products have always tied in.
- Otherwise the previous live read runs exactly as before, and the one caller
  that claims the refresh lease stores its result for the next request. The
  feature therefore self-heals with no cron at all; the cron only keeps a
  customer from ever paying for the rebuild.
- The two control tables are read live on every request, so hiding an Instore
  image or listing takes effect immediately rather than waiting for a rebuild.
  A snapshot superseded that way is rebuilt at once rather than waited out.

**Files and systems affected.**

**Environment.**

- `CRON_SECRET` must be set on the Vercel project before the refresh endpoint
  will accept a call; it fails closed without it. Nothing depends on it: the
  stored collection is built by the first customer request that finds it stale.
- `INSTORE_CATALOGUE_TTL_MS` (optional) sets how old a served snapshot may be.
  Default 150,000 ms; capped at one hour; an invalid value falls back to the
  default rather than widening it. `0` disables the stored path entirely and
  restores the previous live-read-only behaviour.

## Instore refresh cron removed from vercel.json

**Time:** 15:05 SAST

The Vercel deployment failed after the change above. The only plan-sensitive
thing it added was a `* * * * *` entry in `vercel.json` `crons`, which Vercel
rejects at configuration-validation time on the Hobby plan (2 cron jobs, once
per day); that fails preview and production builds alike. This project had no
crons before, while the admin project runs several at `*/10`, so the two are
probably not on the same plan.

- `vercel.json` — removed the `crons` block. `maxDuration: 60` for
  `api/instore-catalogue-refresh.js` stays.
- No code change. `api/instore-catalogue-refresh.js` is unchanged and still
  callable with `CRON_SECRET`; only the schedule that called it is gone.

Instore Products is fully functional without it, because the stored collection
self-heals: a request that finds no fresh snapshot takes the previous live read
and the one caller holding the refresh lease stores the result. The cost is that
roughly one request per `INSTORE_CATALOGUE_TTL_MS` (default 150 s) pays the old
rebuild time instead of none of them.

To restore the warming, any scheduler can call the endpoint. `pg_cron` is
available and `pg_net` is already installed on the stock project, so it can also
be scheduled from the database, independently of the Vercel plan. Not done:
it would put `CRON_SECRET` in a second place and had not been asked for.

**Verification.** `vercel.json` parses and no longer carries a `crons` key.
`npm test` — 373 tests pass. `npm run build` — succeeds.
