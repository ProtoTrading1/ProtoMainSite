## Instore Products served from a stored read model

**Time:** 14:20 SAST

**Summary.** Instore Products was rebuilt from source on every customer
request: a complete paged read of `extended_range_items` (5,336 rows today), a
complete paged read of `website_stock` (6,069 rows) for the duplicate gate, then
the image, price, stock, duplicate and classification rules in JavaScript —
roughly 4,200 products classified and ~150 million identifier comparisons before
the first of sixty products could be shown. The already-gated result is now kept
in its own table in the stock database and a browse or search request reads one
small page from it.

Customer-visible behaviour is unchanged: the same eligibility rules, the same
product objects, the same browse tiles, the same search matching and ranking,
the same paging, the same `source` label and the same response shape. Nothing
about checkout or the live "Check stock" button changed.

**How it works.**

- `api/instore-catalogue-refresh.js` (new) runs the same live read the customer
  API runs and stores its result: one row per eligible product holding that
  product's exact response payload, its browse category, its search tokens and
  its position in the default customer ordering, plus the browse tiles for the
  whole collection. Rows are staged and swapped in one transaction, so a
  half-written or empty collection can never be served.
- `api/extended-range.js` serves from that table when the snapshot is fresh and
  was built under the Instore image/listing controls currently in force. A
  landing or category page is ordered, paged and counted by the database. A
  search is still matched and ranked by the application; the database only
  narrows the collection to the stored token matches first, in SKU order, which
  is the order equal-scoring products have always tied in.
- Otherwise the previous live read runs exactly as before, and the one caller
  that claims the refresh lease stores its result for the next request. The
  feature therefore self-heals with no cron at all; the cron only keeps a
  customer from ever paying for the rebuild.
- The two control tables are read live on every request, so hiding an Instore
  image or listing takes effect immediately rather than waiting for a rebuild.
  A snapshot superseded that way is rebuilt at once rather than waited out.

**Files and systems affected.**

- `api/_instore-catalogue.js` (new) — stored read model: tokens, ordering,
  fingerprints, freshness, paged reads, staged writes.
- `api/instore-catalogue-refresh.js` (new) — `CRON_SECRET`-protected refresh,
  callable from any scheduler. Not registered as a Vercel cron: see the
  follow-up entry below.
- `api/_complete-rows.js` (new) — `readCompleteRows`, extracted so both the
  live read and the stored read model can use it. Re-exported from
  `api/extended-range.js` for existing callers.
- `api/extended-range.js` — the live read is now `loadLiveInstoreCatalogue()`;
  added the stored fast path, the refresh claim and the snapshot write.
- `lib/instore-discovery.mjs` — exported `searchTerms()` and
  `instoreSearchTokens()`, the two halves of `matchesInstoreSearch()`, so the
  stored tokens are the matcher's own tokens rather than a second dialect.
  Matching behaviour is unchanged.
- `vercel.json` — `maxDuration: 60` for the refresh route.
- `tests/instore-catalogue-store.test.js` (new).
- Stock Supabase project `yiqsvwajozafvalwcero`: new tables
  `instore_catalogue`, `instore_catalogue_staging`, `instore_catalogue_state`
  and four service-role-only functions. Applied — see the Proto_Admin journal
  entry for migration `070_instore_catalogue.sql`.

**Environment.**

- `CRON_SECRET` must be set on the Vercel project before the refresh endpoint
  will accept a call; it fails closed without it. Nothing depends on it: the
  stored collection is built by the first customer request that finds it stale.
- `INSTORE_CATALOGUE_TTL_MS` (optional) sets how old a served snapshot may be.
  Default 150,000 ms; capped at one hour; an invalid value falls back to the
  default rather than widening it. `0` disables the stored path entirely and
  restores the previous live-read-only behaviour.

## Instore refresh cron removed from vercel.json

**Time:** 15:05 SAST

The Vercel deployment failed after the change above. The only plan-sensitive
thing it added was a `* * * * *` entry in `vercel.json` `crons`, which Vercel
rejects at configuration-validation time on the Hobby plan (2 cron jobs, once
per day); that fails preview and production builds alike. This project had no
crons before, while the admin project runs several at `*/10`, so the two are
probably not on the same plan.

- `vercel.json` — removed the `crons` block. `maxDuration: 60` for
  `api/instore-catalogue-refresh.js` stays.
- No code change. `api/instore-catalogue-refresh.js` is unchanged and still
  callable with `CRON_SECRET`; only the schedule that called it is gone.

Instore Products is fully functional without it, because the stored collection
self-heals: a request that finds no fresh snapshot takes the previous live read
and the one caller holding the refresh lease stores the result. The cost is that
roughly one request per `INSTORE_CATALOGUE_TTL_MS` (default 150 s) pays the old
rebuild time instead of none of them.

To restore the warming, any scheduler can call the endpoint. `pg_cron` is
available and `pg_net` is already installed on the stock project, so it can also
be scheduled from the database, independently of the Vercel plan. Not done:
it would put `CRON_SECRET` in a second place and had not been asked for.

**Verification.** `vercel.json` parses and no longer carries a `crons` key.
`npm test` — 373 tests pass. `npm run build` — succeeds.

## Instore Products: browser caching and instant local browsing

**Time:** 16:40 SAST

**Summary.** The server-side work above is not yet deployed (`origin/main` is
still at `bcaab62`), so production is unchanged and still slow. Separately,
there was effectively no browser cache: `src/lib/extendedRange.js` held
responses in a module-level `Map` for 30 s, which is lost on every page load,
and the API sends `Cache-Control: private, no-store`, so the browser stored
nothing. Every visit, reload and search was a fresh round trip.

Three changes, all on the client:

1. **A view already seen is painted at once.** Page responses are stored in
   `sessionStorage` and shown immediately on a new page load while the fresh
   response is fetched in the background, so returning to Instore Products no
   longer starts from an empty grid and a spinner.
2. **The whole collection is fetched once per tab, and then nothing is.** The
   API's existing `?catalogue=1` returns the complete already-verified
   collection. It is now fetched in the background — after the first page is on
   screen, while the browser is idle, and never on a `saveData` or 2G
   connection. From then on every search, category tile and page button is
   answered from memory with no request and no spinner. This wires up
   `localPage`, which was written for exactly this and left unused.
3. **Classifying and tokenising a product are memoised per object.** Both are
   pure functions of fields that are never mutated, and the same objects were
   being walked several times per request or search (feed build, filter, sort,
   tiles). This is what makes filtering thousands of products in the browser
   viable, and it speeds up the server's live read too.

**Files affected.**

- `lib/instore-page.mjs` (new) — `instorePage()`: one definition of which
  products match a view, in what order, and which of them a page shows. Used by
  `api/extended-range.js` (live path, stored search path and the isolated
  preview) and by the page once it holds the collection, so a locally answered
  search cannot drift from a server-answered one. It decides nothing about
  eligibility.
- `lib/instore-response-cache.mjs` (new) — the cache windows and the rules for
  which stored response may be shown, separated out so they are testable.
- `lib/instore-discovery.mjs` — memoised `discoveryGroup()` and
  `instoreSearchTokens()` per product object via `WeakMap`. Same results.
- `src/lib/extendedRange.js` — `sessionStorage` persistence,
  `storedExtendedRange()`, `loadInstoreCatalogue()`, `instoreCatalogue()`,
  `clearStoredInstoreResponses()`. Every storage read and write tolerates a
  private window, blocked site data and a full quota.
- `src/lib/auth.js` — `signOut()` clears the stored browsing data first.
- `src/components/ExtendedRangePage.jsx` — paint from the stored view, answer
  locally once the collection is held, deferred and connection-aware prefetch.
- `api/extended-range.js` — uses the shared `instorePage()` instead of its own
  copy of the filter-and-rank rules.
- `tests/instore-browser-cache.test.js` (new).

**What a customer may now see that they could not before.** A view up to five
minutes old, for the moment it takes the fresh response to arrive, instead of a
spinner. Nothing else: the products are the same eligibility-gated products, the
local view is computed by the API's own page definition over the products the
API sent, and checkout and the live stock check are untouched.

**Storage.** `sessionStorage` only — per tab, dropped when the tab closes,
cleared on sign-out. At most 8 page responses, each under 512 KB; the
multi-megabyte collection payload is held in memory and never written to
storage.

**Verification.**

- `tests/instore-catalogue-store.test.js` gained a test that takes the
  `?catalogue=1` payload the browser caches and asserts that `instorePage()` over
  it returns the same products and total as the served response, for seven
  request shapes including two categories, three searches and a second page.
- `tests/instore-browser-cache.test.js` covers the view key (including nonsense
  page numbers), which stored responses may be shown (age window, clock change,

- `npm test` — 381 tests pass. `npm run build` — succeeds. `npm run lint` — one
  pre-existing `no-unused-vars` (`choose`) remains in `ExtendedRangePage.jsx`.

**Deployment status.** Pushed to `claude/youthful-bohr-dhob72`. **Not deployed:
