# 2026-09-25

## Instore Products: instant open, warmed images, one-round-trip cold read

**Time:** 00:30 SAST

**Summary.** Three remaining causes of a slow-feeling Instore Products, found by
looking at what was actually still on the path rather than at the data layer
again.

**1. The free local read was queued behind `requestIdleCallback`.** The previous
change persisted the collection in IndexedDB but routed every caller through
`prefetchInstoreCatalogue()`, which defers to an idle moment. The idle wait was
there to keep a multi-megabyte *download* off the critical path — but it also
deferred reading the copy already on disk, which costs nothing. Opening the
section therefore waited for idle before it even looked locally.

`hydrateInstoreCatalogue()` now does the local read with no guards and no
waiting, and only the network download goes through the idle and connection
guards (`fetchWhenIdle()`). Portal boot calls the local read immediately and
leaves only the download queued behind the main catalogue payload. The page
makes no paged request at all until the local store has been consulted
(`localChecked`), so a browser that already holds the collection renders it with
zero network.

**2. Instore card images were never preloaded.** The main catalogue warms its
first 60 card thumbnails at boot (`preloadCatalogImages`); Instore warmed none,
so its images only began downloading once the grid mounted — which is what
"products loading slowly" looks like to a shopper even when the data is already
there. The first screenful (24, in the real landing order via `instorePage`) is
now warmed whenever the collection is hydrated or downloaded, through the same
`preloadProductImages` helper and therefore the same 400px WebP transform and
the same `saveData`/2G guard. Instore images are on Supabase storage, so that
transform already applied to them; only the warming was missing.

**3. A cold landing page cost two sequential database round trips.** The
serverless function read the snapshot state and both control tables, then the
page of products. Migration 072 adds `instore_catalogue_view(category, from,
limit)`, a read-only function returning freshness, tiles, the current hidden
controls, the total and the page in one call. The caller still derives the
control fingerprint from the SKUs the call returns and compares it to the
snapshot's own, so a snapshot built under superseded controls is refused exactly
as before. Used only where it is the whole answer — not for a search, not for
`?catalogue=1` — and any failure, including a database without 072 applied,
falls through to the reads it replaces.

**Files affected.** `src/lib/extendedRange.js`, `src/lib/products.js`,
`src/components/ExtendedRangePage.jsx`, `api/_instore-catalogue.js`,
`api/extended-range.js`, `tests/instore-catalogue-store.test.js`,
`tests/instore-browser-cache.test.js`. Stock Supabase project: migration
`072_instore_catalogue_view.sql` (in Proto_Admin), applied.

**Verification.**

- `readCatalogueView` is asserted to return exactly what the two reads it
  replaces return — same products and same total — across seven request shapes
  including three landing pages, three categories and a page past the end of a
  category, and the whole served body is still asserted equal to the live read's
  body. Two further tests cover the fingerprint it derives and that a superseded
  snapshot is still refused through it.
- The new function was exercised against production data before wiring: 60
  products with a total of 4,280 and 13 tiles for the landing page, 0 products
  with a total of 50 for Bracelets page 2, the three real hidden listings
  returned, and its first product confirmed to match the stored sort order.
  It is read-only, so unlike migration 070 it is not exposed to the
  `safeupdate` guard that broke that one.
- Tests assert the local read is not behind `requestIdleCallback` while the
  download is, that boot reads locally before queueing the download, that the
  page makes no request until the local store is consulted, and that the landing
  images are warmed from both the stored copy and a fresh download.
- Two assertions from the previous change were updated: they described the
  earlier control flow, not a regression.
- `npm test` — 390 tests pass. `npm run build` — succeeds. 13 Playwright e2e
  tests pass. `npm run lint` — one pre-existing `no-unused-vars` (`choose`).

**What a customer sees.** After the first visit on a device, opening Instore
Products makes no request and no image fetch for the first screen: the
collection comes from IndexedDB and the thumbnails are already in the browser
cache. Search, category tiles and paging were already local. A genuinely cold
first visit is now one database round trip for its first page instead of two.

**Deployment status.** Merged to `main` and deployed. Migration 072 applied to
the production stock database.
