# 2026-10-07

## Restored Instore basket lines failing checkout

**Time:** SAST, afternoon.

**Summary:** Customers whose basket was saved to and restored from their account
could not send an order containing Instore products ("Product on order line N is
unavailable", then a stuck "earlier order request needs confirmation" retry).
`api/account-cart.js` `sanitizeProduct()` dropped `isExtendedRange`, so restored
Instore lines were checked against the main catalogue (`website_stock`), where
they do not exist.

**Changes:**
- `api/account-cart.js`: persist `isExtendedRange` on saved basket lines.
- `api/send-order.js`: classify lines on the server. An unflagged line whose SKU
  is in `extended_range_items` and not in `website_stock` (by SKU or barcode) is
  routed to the Instore resolver. A classification lookup failure falls back to
  the browser flag. Main-catalogue error messages now report the basket's own
  line number instead of the position within the main-catalogue group.
- `src/App.jsx`: the checkout payload never carried `isExtendedRange` at all
  (only id/sku/code/name/snapshot were sent), so the server classification is
  the real fix; the flag is now sent as a hint when known.
- `tests/instore-line-classification.test.js`: new coverage.
- Final review: original mixed CRLF/LF line endings restored in `api/` so the
  diff holds only the content change.

**Impact (read-only check):** 12 saved account baskets held 65 Instore lines,
all missing the flag. No stored basket, order, or catalogue data was modified;
the server fix makes those baskets (and pending retries) submit as-is.

**Verification:** `node --test` 628/628 pass; `npm run build` succeeds; the
checkout/basket Playwright specs pass locally (see PR CI for the full run).

**Deployment:** pushed to branch `claude/tender-gates-ab9i2j` and opened as a
pull request to `main` (Vercel deploys on merge):
https://github.com/ProtoTrading1/ProtoMainSite/pull/266

## Instore checkout no longer gated on live stock (owner decision)

**Time:** ~21:55 SAST.

**Summary:** The owner decided Instore order *requests* must go through
regardless of live Positill stock; the team confirms availability when packing.
`api/send-order.js` no longer rejects an Instore line for low, zero or

## Rejected order requests no longer lock the basket

**Time:** ~22:15 SAST.

**Summary:** After a rejected checkout (for example the Instore stock gate), the
browser kept the request as "needs confirmation" and blocked every later
checkout with a popup until the customer pressed Try again. Owner decision:
customers must simply be able to check out. `src/App.jsx` now (1) drops the
stored request on a definitive 4xx rejection, which the server only returns
before any order is captured (401, review-required, reference-conflict and
promo-in-progress outcomes still keep it); (2) on page load, an unconfirmed
request no longer opens the popup: the next checkout reuses its reference so
the server returns the earlier order if it was captured and refuses a duplicate
otherwise; (3) only an order the server already received, with unfinished
cleanup, still blocks a fresh checkout. This also clears the locks left in
customers' browsers by today's failures without any action on their side.

**Files:** `src/App.jsx`, `e2e/checkout-pending-recovery.spec.js`.

**Verification:** `node --test` 629/629; `npm run build` clean; Playwright
`checkout-pending-recovery` 14/14 and the basket/analytics specs 32 passed
locally (new case: a 409 rejection releases the stored request).

**Deployment:** https://github.com/ProtoTrading1/ProtoMainSite/pull/267
