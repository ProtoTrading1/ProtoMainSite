# 2026-10-07

## Restored Instore basket lines failing checkout

**Time:** SAST, afternoon.

**Summary:** Customers whose basket was saved to and restored from their account
could not send an order containing Instore products ("Product on order line N is
unavailable", then a stuck "earlier order request needs confirmation" retry).
`api/account-cart.js` `sanitizeProduct()` dropped `isExtendedRange`, so restored
Instore lines were checked against the main catalogue (`website_stock`), where
they do not exist.

**Changes:**
- `api/account-cart.js`: persist `isExtendedRange` on saved basket lines.
- `api/send-order.js`: classify lines on the server. An unflagged line whose SKU
  is in `extended_range_items` and not in `website_stock` (by SKU or barcode) is
  routed to the Instore resolver. A classification lookup failure falls back to
  the browser flag. Main-catalogue error messages now report the basket's own
  line number instead of the position within the main-catalogue group.
- `src/App.jsx`: the checkout payload never carried `isExtendedRange` at all
  (only id/sku/code/name/snapshot were sent), so the server classification is
  the real fix; the flag is now sent as a hint when known.
- `tests/instore-line-classification.test.js`: new coverage.
- Final review: original mixed CRLF/LF line endings restored in `api/` so the
  diff holds only the content change.

**Impact (read-only check):** 12 saved account baskets held 65 Instore lines,
all missing the flag. No stored basket, order, or catalogue data was modified;
the server fix makes those baskets (and pending retries) submit as-is.

**Verification:** `node --test` 628/628 pass; `npm run build` succeeds; the
checkout/basket Playwright specs pass locally (see PR CI for the full run).
